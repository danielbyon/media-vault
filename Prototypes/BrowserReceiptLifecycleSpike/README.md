# Browser Receipt Lifecycle Spike

This disposable iOS/iPadOS experiment tests an explicit, unauthenticated HTTP(S) GET entering app-controlled receipt staging. The local fixture uses loopback HTTP. It does not add a production browser action or a production receipt API.

## Receipt boundary

The host allocates transfer, asset, and resource UUIDs before starting a background `URLSessionDownloadTask`. The task description contains only those UUIDs. The configured session attaches no Cookie or Authorization header. Foundation may retain the request URL as part of the system-owned background task; the app does not persist it in its own receipt metadata or diagnostic events.

The download delegate calls `ReceiptStore.publish` synchronously before returning the system temporary URL. The store creates the provisional receipt exclusively with one writable descriptor, requests backup exclusion and `.completeUnlessOpen` protection, and checks the protection attribute before any private byte is written. It keeps that original descriptor open through streaming and synchronization; it never closes a protected file and reopens it for writing. The store checks the exact transfer length, renames the receipt within the same directory, and synchronizes that directory. It then creates a separate opaque manifest with `.completeUntilFirstUserAuthentication`, synchronizes and atomically renames it, and synchronizes the metadata directory. **The metadata directory synchronization after the final rename is the acceptance commit point.** A thrown error before that point does not report acceptance; recovery may still find a published manifest if interruption occurred after its rename.

The receipt-byte directory and each receipt file request `.completeUnlessOpen`. Before transfer, an empty child created without explicit attributes probes directory inheritance; the host records its reported protection and removes it. The metadata directory uses `.completeUntilFirstUserAuthentication` so a process relaunched after the device has first been unlocked can inspect opaque IDs while the device is locked. A receipt file created while locked may remain writable through its original open handle, but cannot be assumed reopenable after that handle closes until device unlock. `discoverMetadata` does not read bytes. `verifyAfterUnlock` is the explicit byte-reopen seam. A simulator returning nil protection attributes is **UNVERIFIED**; a physical device returning nil fails publication before any private byte is written. Canonical resources and vault SQLite remain under their existing `.complete` policy.

Provisional files and receipt bytes lacking any manifest are unaccepted artifacts and may be removed after restart. Malformed published metadata is quarantined for inspection rather than deleting bytes that a prior process may have reported accepted. Repeated scans never create a second publication. File and directory synchronization plus atomic rename define the process-interruption experiment; these tests do not demonstrate sudden power-loss durability.

The entire disposable receipt-staging subtree, each provisional/published receipt and manifest, and the host's acquisition event log request `isExcludedFromBackup`. The store verifies the resource value after each receipt and manifest rename. Ordinary failures before manifest publication remove incomplete files; injected interruption tests retain them for recovery. Backup exclusion is a request to the operating system's ordinary backup policy, not an absolute guarantee that no copy can exist. This spike does not change canonical vault backup behavior.

The focused receipt-store tests inject a stop before protected-file creation and after each publication step. Separate tests delete the simulated URLSession temporary file before and after preservation, then reconstruct the store and check whether an accepted receipt remains. The package tests inject stops before and after journal `.received`, after validation, after canonical commit, and after test-only receipt cleanup. Each uses a fresh SQLite connection and repeated importer reconciliation to check exact bytes and one visible asset. These are deterministic process-boundary models, not hardware crash or sudden-power-loss tests.

## Test-only journal handoff

The runner matches a host manifest and receipt against an independent server record by transfer ID, byte count, and SHA-256. It supplies the exact matching bytes and manifest to a `MediaLibraryTests` case through simulator test environment variables. That case creates one existing vault SQLite journal entry in `.received`, reopens a fresh connection, and invokes the existing importer. The runner transfers bytes across test containers; **the package test imports a copy, not the same physical protected file**. This tests the journal seam after a synthetic unlock gate. It does not prove production vault authentication, a production host-to-journal API, or Data Protection inheritance across that copy.

The host has no MediaLibrary or SQLite dependency and never opens vault state. Its UI's “Explicit test unlock” button only permits byte verification. It is not actual authentication and does not unlock the device.

The simulator lifecycle tests send a slow GET, press Home, observe the app's background scene phase, and reactivate it. The independent fixture must show the same transfer completing before the app records acceptance. This exercises simulator backgrounding, not proven OS suspension or a system-initiated relaunch. A separate fixture withholds its response; a five-second app-owned test timeout cancels that GET, with zero bytes sent and no accepted receipt. It is not a measurement of URLSession's own timeout policy.

For a physical-device attempt, the same fixture can bind one explicit RFC 1918 interface using `SPIKE6_BIND_HOST`. `SPIKE6_SLOW_CHUNK_DELAY` may extend the existing slow route's fixed-chunk delay from 0.025 to at most 0.2 seconds; it adds no route or credential behavior. The physical host's **built** Info.plist must contain `Spike6FixtureHost` with that numeric private IPv4 address and a narrow HTTP transport exception for the same address; the app still constructs only the three fixed `/media/` routes on port 18756. This target uses a static Info.plist, so an `INFOPLIST_KEY_Spike6FixtureHost` command-line build setting alone does not inject the key. An omitted key keeps simulator loopback. XCTest's supported hardware-button API does not provide a lock button, so the physical-only UI case emits `SPIKE6_LOCK_NOW` and `SPIKE6_UNLOCK_NOW` markers around a 65-second background window for manual device interaction. A test pass without independently confirmed device locking remains unverified. A passing simulator test or a successful unlocked device transfer alone does not establish locked-device Data Protection; record lock/unlock and file-attribute evidence separately.

## Run and evidence

Run `make spike-browser-receipt-lifecycle` from the isolated worktree with GNU `gtimeout` available. The runner starts the independent fixture, runs the receipt-store and fixture unit tests, uninstalls the disposable host to begin each simulator matrix with an empty container, then runs five UI tests and two package tests (including five dynamic interruption cases) serially on iPhone 17 and iPad Pro 11-inch (M5) simulators. It writes `.xcresult` bundles, sanitized app/fixture events, a correlated lifecycle summary, and a handoff summary under an ignored `.build/spike6-run-*` directory. Any test assertion or evidence-correlation failure returns nonzero. A five-minute Xcode test or diagnostics timeout returns a distinct nonzero status, even if the test log reports passing assertions. Missing physical hardware is recorded separately as unverified.

Initial physical builds failed before installation because Xcode lacked a usable development account or provisioning profile for the disposable bundle IDs. After account setup and a manual Build For Testing, a temporary, ignored host Info.plist gave only the fixed fixture's private IPv4 address an HTTP exception. The disposable host then ran on an iPhone 17 Pro Max with a USB connection. A passing unlocked-device control did not count as locked-device evidence. In a separate run, the operator confirmed that the phone remained locked from the `SPIKE6_LOCK_NOW` signal until after the independent fixture finished its 8,388,690-byte response. The app's on-device event log reports receipt acceptance in the background before foreground activation, `.completeUnlessOpen` for the receipt file, receipt directory, and inheritance probe, and verification after the test unlock gate. The exported receipt bytes, manifest, event, and fixture record agree on identity, byte count, and SHA-256. This demonstrates a protected receipt created during the confirmed lock interval. It does not demonstrate reopening the closed file while still locked, a physical canonical file's `.complete` class, genuine system-initiated relaunch, sudden-power-loss durability, or production vault authentication. The temporary fixture Info.plist and signing edits were not retained in the reviewed project source.

The server records fixed fixture paths and opaque correlation IDs. The app records fixed event names, UUIDs, counts, digests, protection reports, and error codes. The runner enforces exact event/fixture field names, types, and permitted values and rejects a request that carried Cookie or Authorization. Do not publish raw result bundles without separate inspection.

Apple documents the closed-file behavior of [`.completeUnlessOpen`](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeunlessopen) and the [backup-exclusion resource value](https://developer.apple.com/documentation/foundation/urlresourcevalues/isexcludedfrombackup). The latter is a backup-policy request and can be reset by file operations; this experiment checks its value after each publication rename.
